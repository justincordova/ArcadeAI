# ArcadeAI — Specification

## 1. Overview

ArcadeAI is a CodeWisp-style web app that turns natural-language prompts into playable 2D browser games. Users sign in, type a prompt, and watch a single-file HTML5 canvas game stream into an iframe within seconds. They iterate on the result via a chat loop, manage their library of games from a dashboard, and operate within a credit-based usage model with tiered plans. Games can be published to a public read-only player and remixed into a new owned game.

The core architectural bet: **single-file HTML5 canvas games, generated by a strong LLM, executed in a sandboxed iframe, refined through a chat loop, scoped to authenticated users with persistent storage.**

This is a working prototype heading to its first deployment. No real billing, no external email. The architecture is structured so a future productionization path is straightforward (swap SQLite for Postgres, wire Stripe into the existing billing endpoint, add a real email provider).

## 2. Scope

### In scope

- OAuth authentication via Google and GitHub (no email/password), with account linking and last-provider-guarded unlink
- Default display name from OAuth profile, falls back to `user-{8 hex chars}` if blank, user-editable
- Multi-game dashboard per user (grid of game cards with screenshot thumbnails, list view, loading skeletons, prefetch on hover)
- Single-file HTML + JS games using HTML5 Canvas
- 2D arcade genres: paddle, snake, flappy, shooter, platformer, puzzle, runner, other
- Prompt → game in one shot (streaming)
- Refinement via follow-up instructions
- Auto-repair on runtime errors (capped attempts)
- Public sharing: publish a game to a stable `/play/<slug>` URL; remix any public game into your own library
- Public Discover gallery (trending / top / new sorts, genre filter, likes, play counts) with OG/Twitter unfurl images for shared links
- Single-level undo of the last refinement/repair
- Credit-based usage model with daily and monthly caps
- Lifetime trial cap for the free tier (deployment-phase throttle, single config flip to revert)
- Tiered plans: Free, Creator, Pro, Enterprise (display only) + internal Admin tier
- Pricing page with monthly/yearly toggle (upgrade buttons are no-ops in prototype)
- User dropdown with usage bars, plan badge with reset countdown, cost preview on prompt submit
- Profile settings page with connected-accounts management (Connect / Disconnect with last-provider guard)
- Dark/light mode toggle
- Pino-based structured logging (request lifecycle, LLM cost, RAG retrieval, refund reason)
- Per-IP and per-user rate limiting
- CSRF defense via Content-Type guard on state-changing routes
- RAG library of curated reference games for few-shot prompting
- Backend test suite (Bun test + Fastify `inject`) and frontend unit tests (Vitest) covering the highest-risk pure modules
- CI on push and PR (lint + build + test)

### Out of scope (MVP)

- Real billing (Stripe integration is structured-for but not implemented)
- Email verification, password reset emails, any outbound email
- Email/password auth
- Full version history UI, in-browser code editor, syntax-highlighted code reveal (a single-level undo of the last refinement/repair IS implemented — see §5)
- Multi-file game projects, frameworks, backends inside generated games
- 3D, multiplayer, mobile-native, leaderboards, asset generation
- Production-grade scaling (Redis-backed concurrency lock, multi-instance, log shipping)
- Mobile responsiveness for the builder view (dashboard and pricing are responsive; builder is desktop-only)
- Adaptive suggestions, genre-card empty state, admin dashboard, in-app feedback widget, PostHog analytics

### Models

| Model | Role |
|---|---|
| Claude Sonnet 4.6 (`claude-sonnet-4-6`) | **Runtime:** game generation, refinement, auto-repair (anything where output quality determines whether the game is fun) |
| GPT-4.1-mini (`gpt-4.1-mini`) | Genre classification, style tag extraction, code summarization, error categorization, game title generation |
| text-embedding-3-small | Prompt embeddings for RAG retrieval |

The RAG reference library (~20 hand-curated games — see §8) is generated **manually by the development team using an external LLM session**, not via a build-time API call from this codebase. No model id for the reference-drafting step appears anywhere in the runtime or build pipeline; the curated HTML is the editorial source of truth.

Model IDs are pinned in `packages/shared/src/models.ts` so they're swappable in one place.

The split keeps cost low on bulk operations while reserving Sonnet for the work that actually determines quality.

## 5. Data Model

### Tables

```ts
// users — extended from Better Auth's user table
users
  id              text primary key (better-auth uuid)
  email           text unique not null     // sourced from OAuth provider
  display_name    text not null            // OAuth name field, or 'user-{8 hex}' if blank. Not unique.
  tier            text not null            // 'free' | 'creator' | 'pro' | 'admin' (Drizzle enum-typed)
  credits_remaining_daily   integer not null
  credits_remaining_monthly integer not null
  daily_reset_at    integer not null  // unix ms, next UTC midnight
  monthly_reset_at  integer not null  // unix ms, first of next month UTC
  // Lifetime counters used by the temporary deployment-phase free-tier policy
  // (see §10). Monotonically incremented on success, decremented only on
  // refund. Exist for all tiers so the schema is consistent, but are only
  // enforced when ENFORCE_LIFETIME_LIMITS_FOR_FREE is true and tier === 'free'.
  lifetime_generations_used integer not null default 0
  lifetime_refinements_used integer not null default 0
  theme           text not null default 'dark'  // 'dark' | 'light' | 'system' (enum-typed)
  created_at      integer not null
  updated_at      integer not null

games
  id              text primary key (uuid)
  user_id         text not null references users(id) on delete cascade
  title           text not null
  current_code    text not null     // the latest single-file HTML
  previous_code   text              // single-level undo snapshot; null when nothing to undo
  thumbnail       text              // base64 PNG data URL or null
  genre           text              // classified genre bucket (enum-typed; one of the 8 §6 buckets)
  original_prompt text not null
  // Public sharing (§11.5). is_public toggles visibility on /play/<slug>;
  // public_slug is generated on first publish and retained on unpublish so
  // re-publishing keeps the same URL. remixed_from_game_id is a soft pointer
  // to the source of a remix (no FK reference — would require ordering
  // gymnastics in Drizzle's self-reference handling).
  is_public         integer not null default 0   // 0 | 1
  public_slug       text unique                  // 8 hex chars, or null
  published_at      integer
  remixed_from_game_id text
  created_at      integer not null
  updated_at      integer not null

messages
  id              text primary key (uuid)
  game_id         text not null references games(id) on delete cascade
  kind            text not null     // 'prompt' | 'feedback' | 'summary' (enum-typed)
  content         text not null     // user prompt/feedback (verbatim), or an AI-generated change summary
  created_at      integer not null

// Note: assistant output (generated HTML) is NOT stored here. Only the *latest* HTML
// lives in `games.current_code` (with one prior step in `games.previous_code`).
// `kind='summary'` rows hold a short AI-generated description of what a refinement
// changed (rendered under the turn in the chat panel). Auto-repair attempts are NOT
// stored as messages (they're tracked in `usage_log` with action='repair'). The chat
// panel renders user messages with implicit "→ Generated game" markers between entries.

usage_log
  id              text primary key (uuid)
  user_id         text not null references users(id) on delete cascade
  game_id         text references games(id) on delete set null
  action          text not null     // 'generation' | 'refinement' | 'repair' (enum-typed; repair logged but charges 0)
  credits_charged integer not null
  // True if this deduct also incremented the user's lifetime counter (free
  // tier + ENFORCE_LIFETIME_LIMITS_FOR_FREE). Refund consults this to decide
  // whether to decrement the counter back, independent of the current tier
  // or flag value (which may have changed since deduct).
  lifetime_counter_incremented integer not null default 0
  succeeded       integer not null  // 0 or 1
  refunded_at     integer           // unix ms when credits were refunded; null if never refunded. Set once; refund is idempotent on this column.
  created_at      integer not null

// RAG library — curated reference games
rag_examples
  id              text primary key
  genre           text not null     // one of the 8 genre buckets
  prompt          text not null     // the prompt that would describe this example
  html            text not null     // the full single-file HTML
  created_at      integer not null

// vec0 virtual table for embeddings, joined to rag_examples by id.
// `genre` is duplicated here as a vec0 metadata column so the retrieval query
// can filter and rank in a single statement (see §8).
rag_embeddings    vec0 virtual table (id text primary key, genre text, embedding float[1536])
```

The `vec0` virtual table cannot be expressed in Drizzle's schema DSL. It's created via a **post-migration raw SQL step** that runs after Drizzle migrations: `CREATE VIRTUAL TABLE IF NOT EXISTS rag_embeddings USING vec0(id text primary key, genre text, embedding float[1536])`. This is a one-line script in `packages/db/src/post-migrate.ts` invoked after `drizzle-kit migrate`. The `genre` column is duplicated from `rag_examples` so the single-query genre-filtered retrieval in §8 works without a JOIN.

Better Auth's `session` and `account` tables live alongside, managed by the library. The `account` table stores per-provider OAuth tokens and linkage (one row per linked provider per user).

The `users` table extends Better Auth's built-in `user` table with our custom columns (`tier`, `credits_remaining_*`, `*_reset_at`, `theme`, `display_name`) using Better Auth's schema customization (additional fields are declared in the auth config and Better Auth includes them in its generated migrations). On first sign-in, Better Auth's `databaseHooks.user.create.before` callback populates our extended fields (admin tier check, initial credit allotment, default display_name).

### Key design points

- **Latest code + single-level undo.** No full version history in MVP. Each refinement/repair overwrites `games.current_code` but first snapshots the prior code into `games.previous_code`. `POST /api/games/:id/undo` atomically swaps `previous_code` back into `current_code` and clears the slot (one step deep, no redo). The guard `WHERE previous_code IS NOT NULL` makes a concurrent double-undo a no-op; `GET /api/games/:id` exposes a `canUndo` boolean (the raw `previous_code` bytes are never shipped to the client).
- **Optimistic credit deduction with refund on failure.** Credits decremented at request start, refunded only if the action fails unrecoverably (not on auto-repaired errors — those are our problem, not the user's).
- **Daily and monthly counters reset lazily on read** (compare current time to `*_reset_at` and reset if past).
- **All timestamps are unix milliseconds (integer)** for SQLite compatibility and JS interop.
- **Lifetime counters are atomic with credit deduction.** The conditional `UPDATE` in `services/usage/charge.ts:deduct()` decrements credits AND increments the lifetime counter in a single statement, so a TOCTOU race between two concurrent free-tier requests can't bypass the cap.
- **Drizzle enum types** narrow `tier`, `genre`, `theme`, `messages.kind`, and `usageLog.action` at the TS layer. DB-level CHECK constraints are deferred (SQLite can't `ALTER TABLE ADD CONSTRAINT`; recreating tables on a live DB isn't worth the marginal gain when Zod already enforces these at the route boundary).

## 6. Genre & Style Classification

### Genre buckets (8)

`paddle, snake, flappy, shooter, platformer, puzzle, runner, other`

Drives RAG retrieval. `other` falls back to no genre filter (nearest-neighbor across the whole library).

### Style tags

Free-form aesthetic descriptors extracted by GPT-4.1-mini (e.g. `retro`, `neon`, `minimal`, `cute`, `dark`). Injected into the Sonnet system prompt as guidance, not used for retrieval.

### Classification call

Single GPT-4.1-mini call (structured output / JSON mode) returns:
```json
{ "genre": "shooter", "style_tags": ["retro", "neon"] }
```

Done in parallel with the embedding call to minimize latency.

### Failure handling

If the classification call returns malformed JSON, an invalid genre, or fails entirely:
- Default to `genre: "other"`, `style_tags: []`
- Log the failure at WARN level with the raw response
- Continue the pipeline (RAG falls back to global nearest-neighbor on `other`)

Generation should never block on classification failure.

## 7. Generation Pipeline

### Initial generation

```
POST /api/games  (game row created immediately with placeholder title;
                  prompt persisted as messages row with kind='prompt')
    ↓
SSE 'meta' event sent: { gameId, placeholderTitle }  (client replaceState → /game/:id)
    ↓
[parallel]
  ├─ GPT-4.1-mini: classify genre + extract style tags
  ├─ text-embedding-3-small: embed prompt
  └─ GPT-4.1-mini: generate game title (PATCH /api/games/:id when complete)
    ↓
sqlite-vec: retrieve top 1 example, filtered by genre
    ↓
Claude Sonnet 4.6: generate single-file HTML (streamed)
    ↓
Stream HTML tokens to client via SSE 'chunk' events
    ↓
Client renders into iframe via srcdoc
    ↓
Client captures thumbnail after ~2s, POSTs to /api/games/:id/thumbnail
```

The placeholder title is the first 40 chars of the prompt. The generated title arrives via the next dashboard load or by polling/refetching `/api/games/:id`. The original prompt is also stored on `games.original_prompt` for use in refinement context.

**Build-order note.** The parallel fanout (genre classification + style tags + embedding + title generation) lands in build-order step 10. Build-order step 4 ships with only the placeholder title (first 40 chars of the prompt) and a hardcoded prompt; the title-generation call, classification call, embedding call, and RAG retrieval are layered on in steps 9 and 10. See §19.

### Refinement

```
User feedback (persisted as messages row with kind='feedback') + current code
    ↓
If currentCode > 2000 tokens (estimated as chars/4): GPT-4.1-mini summarizes into structural digest
    ↓
Build context: original prompt + bulleted history of past user requests + current code (or digest)
    ↓
Claude Sonnet 4.6: generate updated HTML (system prompt allows full rewrite if feedback is incompatible with current code)
    ↓
Stream HTML, replace iframe srcdoc, recapture thumbnail
```

### Auto-repair

```
iframe postMessage('game-error', {message, stack})
    ↓
Show "Detected an error, fixing..." indicator
    ↓
GPT-4.1-mini: categorize error (syntax / runtime / logic)
    ↓
Claude Sonnet 4.6: repair (current code + error + original prompt)
    ↓
Stream replacement HTML
    ↓
If a 2nd repair fails: show error to user with "Try again" (re-runs original prompt) and "Refine" (treats as refinement turn) buttons
```

Auto-repair is **free** — credits are not charged. The model failed, not the user. Each repair attempt still gets a `usage_log` row with `action='repair'`, `credits_charged=0`, and `succeeded` set on completion (for observability — we want to know how often repairs happen and how often they work).

## 8. RAG Library

### Sourcing

**Manually authored, build-time only.** Target ~20 games at launch (~2–3 per genre bucket).

The reference library is the highest-leverage code in the entire system — every runtime generation retrieves one of these examples and shows it to Sonnet as a "build something like this" reference. A 5% better reference compounds across thousands of generations.

**The reference games are authored by the development team in this conversation (or a separate LLM session), not by an automated script.**

- We (the developers) generate ~20 games using a strong LLM — directly in this conversation or in a separate LLM session — and copy the output into the repo. There is NO build-time script in `apps/server/scripts/` that calls any LLM API to produce reference games. Drafts are produced in the LLM chat session, copied into the repo, then edited and verified.
- Each draft is then hand-edited until it cleanly satisfies the system prompt's structural rules (canvas, gameLoop, title screen, etc.) and plays well in a browser.
- The committed, hand-curated HTML files in `apps/server/scripts/rag-curated/` are the editorial source of truth.
- Runtime model selection is unaffected: Sonnet remains the runtime model for all user-facing generation, refinement, and repair.

### Implementation note (separate doc)

The reference library has its own scope — a manual generation + editorial process, plus embedding and seeding scripts to populate the database. **It is planned and executed in its own design doc** (`docs/designs/09-rag-library.md`) separately from the main app. The embedding (`text-embedding-3-small`) and seed steps are scripted and idempotent; only the upstream "produce the HTML" step is manual. The main app's build order assumes the seeded library exists by step 9.

### Retrieval

- **Exactly 1 example** per generation request. Two examples confuse the model and double input tokens; one strong example is more effective.
- **Full code injected** into the system prompt as a few-shot reference. Skeletons lose the concrete pattern that makes few-shot work.
- **Filtered by classified genre**, then nearest-neighbor by embedding cosine similarity within that filter. `other` genre falls back to global nearest-neighbor.

### Storage

- `rag_examples` holds the metadata + HTML.
- `rag_embeddings` is a `vec0` virtual table holding the 1536-dim embeddings.
- Single SQL query: `SELECT html FROM rag_examples WHERE id IN (SELECT id FROM rag_embeddings WHERE genre = ? ORDER BY vec_distance_cosine(embedding, ?) LIMIT 1)`.

## 9. Sandboxing & Error Handling

### iframe setup

- `<iframe srcdoc={generatedHTML} sandbox="allow-scripts">` (no `allow-same-origin` — that would let generated code escape).
- A wrapper script is injected into the bottom of every generated HTML before assignment to `srcdoc`. The wrapper is the **single canonical file** at `apps/web/src/lib/iframe-wrapper.ts`; every step that adds a behavior extends this one file.

**Required handlers (build-order step 4):**

```js
window.addEventListener('error', (e) => {
  parent.postMessage({type: 'game-error', message: e.message, stack: e.error?.stack}, '*');
});
window.addEventListener('unhandledrejection', (e) => {
  parent.postMessage({type: 'game-error', message: String(e.reason)}, '*');
});
```

**Thumbnail capture handler (build-order step 5):** the wrapper also registers a `message` listener for `{ type: 'capture-thumbnail' }` from the parent. On receipt it serializes the canvas via `canvas.toDataURL('image/png')` and posts back `{ type: 'thumbnail', dataUrl }`. The parent triggers capture only after the relevant SSE stream emits `done` (generation, refinement, or successful repair).

Any future step that extends the wrapper must update this section. The wrapper is **never persisted** — `games.current_code` stores only the LLM's raw output, and the wrapper is appended client-side at every iframe assignment.

### Error scope

- **Hard crashes only** trigger auto-repair (uncaught exceptions, unhandled promise rejections).
- Silent failures (black canvas, no rAF) are not auto-detected — too many false positives kill UX more than the bug does.
- Logic bugs (ball goes through paddle) are user-detected and handled via refinement turns.

### Repair lifecycle

1. Error caught → show "Detected an error, fixing..." indicator (visible, not silent).
2. Categorize → repair → stream replacement.
3. Cap at 2 attempts.
4. After 2 failures: surface error to user with truncated message, collapsible code panel, and two CTAs (Try again / Refine).

### iframe lifecycle on refinement

Hard reload — replacing `srcdoc` re-runs the game from scratch. No hot-swap.

### Tiers

|---|---|---|---|---|

| Creator | $15 | $13/mo ($156 billed yearly, -15%) | 20,000/month, no daily cap | Public |

**Daily counter for paid tiers.** Only Free has an enforced daily cap (500). Creator, Pro, and Admin tiers have no daily cap — the daily counter is decremented for observability but the daily check is skipped. The `users.credits_remaining_daily` and `daily_reset_at` columns still exist and reset for all tiers; they're informational for paid tiers.

### Temporary free-tier lifetime cap (deployment phase)

For the initial public deployment, the free tier is gated by an additional **lifetime** cap to bound runaway cost from anonymous traffic until we have observed real usage:

| Tier | Lifetime generations | Lifetime refinements |
|---|---|---|
| Free | 1 (total, ever) | 3 (total, ever) |

Enforced via `lifetime_generations_used` / `lifetime_refinements_used` on the user row, folded into the same atomic UPDATE that deducts credits. Repairs are exempt (they're free; categorized differently). Configured by `ENFORCE_LIFETIME_LIMITS_FOR_FREE` and `FREE_TIER_LIFETIME_LIMITS` in `packages/shared/src/plans.ts`. **Flip the flag to `false` and redeploy to revert to the standard SPEC §10 limits.** The lifetime columns stay in the DB regardless.

When a free user hits the lifetime cap, the API returns 402 with `code: "FREE_TIER_EXHAUSTED"` and `details.kind: "lifetime"`. The client renders an upgrade-only banner instead of a reset countdown.

### Admin assignment

- `ADMIN_EMAILS` env var (comma-separated).
- On first sign-in, if `email` matches an entry, `tier` is set to `'admin'` automatically (via Better Auth's `databaseHooks.user.create.before`).
- Admin users see "Admin (unlimited)" in the usage dropdown instead of fractional bars.

### Credit lifecycle

1. Request arrives → check `credits_remaining_*` >= action cost AND lifetime guard (Free + flag on).
2. If insufficient → 402 Payment Required (`code: "INSUFFICIENT_CREDITS"` for window exhaustion, `"FREE_TIER_EXHAUSTED"` for lifetime).
3. If sufficient → deduct optimistically (atomic UPDATE — see §5 key design points), log to `usage_log` with `succeeded = 0` and `refunded_at = null`. The log row records `lifetime_counter_incremented` so refund knows whether to roll the lifetime counter back.
4. On unrecoverable failure → refund credits AND set `refunded_at = now`, leave log row marked `succeeded = 0`. Refund is idempotent on `refunded_at IS NULL` — a second refund call for the same row is a no-op. Refund also decrements the lifetime counter iff the original deduct incremented it.
5. On success (including auto-repaired) → mark log row `succeeded = 1` (do NOT set `refunded_at`).
6. On user-initiated cancel → mark log row `succeeded = 1`, do NOT refund (per §14).

### Refund reasons

`refund(logId, { reason })` records why a refund was issued. Used for log aggregation, not user-facing copy:

| Reason | Source |
|---|---|
| `abort` | Stream errored with `name === 'AbortError'` (user closed the tab) |
| `timeout` | Error message contained "timeout" / "timed out" (server-side LLM cap, see §14) |
| `validation_error` | Pre-stream validation failed after deduct (currently unused — moved to `persistence_error`) |
| `persistence_error` | Pre-stream DB writes / context build failed after deduct, or the game row vanished mid-stream (deleted in another tab) |
| `stranded` | Reclaimed by the reconciliation sweep from a stream whose process was killed before it could finalize (see below) |
| `llm_error` | Anything else — LLM 5xx, parse failure, etc. |

The reason is observability metadata only — it is logged with the refund, not
stored on `usage_log`, so adding a member needs no migration.

### Stranded-stream reconciliation

`deduct()` charges and increments the lifetime counter *before* the LLM call,
and only a handler that runs to completion converts the `usage_log` row into
`markSucceeded` or `refund`. A process killed in between leaves it at
`succeeded = 0 AND refunded_at IS NULL` forever.

That is not hypothetical — the shutdown drain waits 30s for streams that run up
to 180s, and an orchestrator kill timeout can cut it shorter still. On the free
tier, which allows exactly one lifetime generation, the damage is permanent
without reconciliation: credits gone, `lifetime_generations_used` stuck at the
cap so every future generate 402s, and an orphaned game with empty
`current_code` that both refine and publish reject.

`services/usage/reconcile.ts` therefore sweeps on boot and every 5 minutes,
refunding in-flight rows older than `STALE_STREAM_CUTOFF_MS` (15 min — well
past the 180s LLM ceiling plus aux calls, so a genuinely live stream is never
touched, including one owned by another instance). `refund()` is idempotent, so
racing a live handler is safe.

### Reset behavior

- **Daily counter:** resets at UTC midnight. Lazy reset on read.
- **Monthly counter:** resets at first of month UTC. Lazy reset on read.
- **Plan change (prototype):** the balance is capped at `MIN(current, new tier limit)` on every change — it is never topped up on upgrade. Because the prototype has no payment ledger and upgrades are free, a free→creator→free round-trip would otherwise mint creator-tier credits a free user never paid for. So upgrades take effect for the tier/limits but do not grant the new allotment immediately; the user reaches the higher allotment at the next monthly reset. **Target behavior (post-Stripe):** upgrade immediately tops up to the new allotment, since a real payment proves the credits were bought. Implemented in `apps/server/src/routes/billing.ts`; revisit alongside the billing integration.
- **Plan downgrade:** capped at the lower tier's limit via the same `MIN`. (In a real-billing world this would preserve already-paid balance until the next monthly boundary; the prototype cap is the anti-minting stand-in.)

## 11. Backend API

All routes prefixed with `/api`. Auth required except where noted.

### Auth (Better Auth handles these)

These are Better Auth's own route shapes — provider is a body field, not a path
segment. Getting this wrong is silent: the `/api/auth/*` wildcard forwards
anything to Better Auth, which 404s a route it doesn't have.

- `POST /api/auth/sign-in/social` — body `{ provider: 'google' | 'github', callbackURL }`. Returns `{ url }` to navigate to.
- `GET  /api/auth/callback/:provider` — OAuth callback (creates user on first sign-in). Built from `BETTER_AUTH_URL`, so that value must match what's registered with the provider.
- `POST /api/auth/sign-out`
- `GET  /api/auth/session` — current session/user
- `POST /api/auth/link-social` — body `{ provider, callbackURL, disableRedirect }`. Links a second provider to the current session; returns `{ url }` to navigate to.
- `POST /api/auth/unlink-account` — unlink an OAuth provider; Better Auth refuses if it would leave the user with no auth method (last-provider guard).
  Note this route sits behind Better Auth's `freshSessionMiddleware`: sessions
  live 7 days (`expiresIn`) but are "fresh" only 24h (`freshAge`), and a refresh
  extends `expiresAt` without moving `createdAt`. Past hour 25 it returns 403
  `SESSION_NOT_FRESH`, and there is no re-auth flow — the client tells the user
  to sign out and back in. `link-social` uses plain `sessionMiddleware`, so only
  the unlink direction is affected.

On first sign-in:
- User row created with email from OAuth provider
- `display_name` set to provider's name field, or `user-{8 hex}` if blank
- `tier` set to `admin` if email matches `ADMIN_EMAILS`, otherwise `free`
- Initial credit allotment granted

### Generation

- `POST /api/games` — create new game, runs full generation pipeline. Streams SSE. Body: `{ prompt: string }`. Charges 200 credits. Returns `{ gameId, placeholderTitle }` in initial `meta` event (final title arrives later via PATCH), then streams HTML chunks.
- `POST /api/games/:id/refine` — refinement turn. Streams SSE. Body: `{ feedback: string }`. Charges 150 credits.
- `POST /api/games/:id/repair` — auto-invoked by the client when the iframe reports an error via postMessage. Streams SSE. Body: `{ error: { message, stack } }`. Free (charges 0 credits but logged in `usage_log`).

### Game CRUD

Thumbnail bytes are never inlined in a JSON response — they are base64 data
URLs up to 350 KB. Every payload exposes a `hasThumbnail` boolean and the bytes
load lazily by reference from a dedicated image route.

- `GET    /api/games` — list current user's games (id, title, `hasThumbnail`, updated_at). For dashboard.
- `GET    /api/games/:id` — full game (code + messages history) plus `canUndo` and `inProgress`. Excludes `previousCode` (undo restores it server-side) and `thumbnail`.
- `GET    /api/games/:id/thumbnail.png` — owner-scoped PNG bytes, decoded from the stored data URL. Falls back to a placeholder when absent or malformed.
- `PATCH  /api/games/:id` — update title (only mutable field exposed).
- `POST   /api/games/:id/thumbnail` — body: `{ thumbnail: string }` (base64 data URL, ≤350 KB).
- `POST   /api/games/:id/undo` — single-level undo of the last refinement/repair. Atomic guarded swap of `previous_code` into `current_code`. 409 while a stream is in flight for the game, and 409 when there is nothing to undo.
- `DELETE /api/games/:id` — hard delete. `usage_log.game_id` is `ON DELETE SET NULL`, so billing history survives.

### User & usage

- `GET   /api/me` — current user with usage stats (daily + monthly remaining, reset times, tier, linked providers).
- `PATCH /api/me` — update display_name or theme.
- `DELETE /api/me` — delete account + all games + all linked OAuth accounts.

### Billing (no-op in prototype)

- `POST /api/billing/change-plan` — body: `{ tier: 'free' | 'creator' | 'pro', interval: 'monthly' | 'yearly' }`. In prototype, immediately updates user's tier and resets credits. Structured so a future Stripe webhook can replace the immediate update.

### Public sharing

- `POST /api/games/:id/publish` — owner only. Sets `is_public = true` and generates an 8-hex-char `public_slug` on first publish (retry on collision, max 3 attempts). Returns `{ slug, isPublic, publishedAt }`. Slug is retained on subsequent unpublish/republish so the URL stays stable.
- `POST /api/games/:id/unpublish` — owner only. Sets `is_public = false`; the slug stays in the row.
- `GET  /api/play/:slug` — **public**, no auth. Returns `{ id, title, currentCode, originalPrompt, ownerDisplayName, publishedAt, genre, likeCount, playCount, liked }` (no `userId`, no `thumbnail`, no messages, no auth-leaking fields). 404 (not 403) on private/unknown slugs to avoid existence leakage. Slugs are matched case-insensitively at the edge but normalized to lowercase before the lookup, since `public_slug` is case-sensitive.
- `POST   /api/play/:slug/like` / `DELETE /api/play/:slug/like` — auth required. Toggles a like and returns the authoritative `likeCount` via `RETURNING` rather than client arithmetic.
- `POST /api/play/:slug/play` — **public**. Increments the play counter feeding Discover's trending sort. Rate-limited per IP *and* per slug.
- `GET  /api/og/:slug.png` — **public**. OG/Twitter unfurl image for a published game. Fetches only the thumbnail column; serves a placeholder for unknown slugs so crawlers hitting a pre-publish URL still get an image.
- `POST /api/play/:slug/remix` — auth required. Copies `current_code`, `original_prompt`, and `genre` into a new game owned by the caller, sets `remixed_from_game_id` to the source. Charges 0 credits but counts 1 against the free-tier lifetime generation cap so a remix loop can't bypass the throttle.

### Discover

- `GET /api/discover` — **public**, no auth. Paginated list of published games. Query: `sort` (`trending` | `top` | `new`), optional `genre`, `limit` (1–50, default 24), `offset` (0–10 000). Returns `{ items, nextOffset }`; `nextOffset` is null once the next page would exceed the offset cap, so the tail terminates cleanly rather than 400ing. A viewer's session, when present, hydrates `liked` per row. Thumbnail bytes are excluded here too — `hasThumbnail` plus `/api/og/:slug.png`.

### Health

- `GET /api/health` — unauthenticated. Returns `{ ok: true, version: '<package version>' }`. Used for liveness checks and as the smoke test in build step 1.
- `GET /api/config` — unauthenticated. Returns `{ hasAnthropicKey: boolean, hasOpenAiKey: boolean }`. Used by the builder to disable the prompt input with a clear "setup required" banner when the server is missing API keys.

### Error response shape

All `/api/*` errors (4xx and 5xx) return a uniform body:

```ts
{
  code: ErrorCode,            // closed enum — "VALIDATION_ERROR" | "UNAUTHORIZED" |
                              // "NOT_FOUND" | "CONFLICT" | "INSUFFICIENT_CREDITS" |
                              // "FREE_TIER_EXHAUSTED" | "PAYLOAD_TOO_LARGE" |
                              // "RATE_LIMITED" | "INTERNAL_ERROR"
  message: string,            // display copy; may change
  details?: Record<string, unknown>  // case-specific (e.g. { resetAt, kind } for quota)
}
```

Frontend handlers switch on `code`. `apps/server/src/lib/errors.ts` exposes `sendError` and convenience constructors (`validationError`, `notFoundError`, `quotaError`, etc.). Routes that pre-date this shape have all been migrated; the global `setErrorHandler` returns the same shape for uncaught failures.

### SSE streaming format

All streamed endpoints emit `text/event-stream` with these event types:
- `meta` — initial metadata (`{ gameId, placeholderTitle }`). Sent immediately after game row creation, before any LLM work. Final title arrives later when title generation completes (next `GET /api/games/:id` reflects it).
- `chunk` — HTML token (`{ delta: string }`)
- `error` — terminal failure (`{ message: string, code?: string }`)
- `done` — terminator only (`{}`). Client already has full code from accumulated chunks.

## 13. System Prompt Strategy (Sonnet)

We maintain three Sonnet prompt families — all running on Claude Sonnet 4.6:
- **Generation prompt** (with per-genre variants) — initial single-shot game creation
- **Refinement prompt** — applies user feedback to existing code
- **Repair prompt** — fixes a runtime error in existing code

The shared base contract below applies to all three. Variants extend it with task-specific instructions.

### Base contract

The Sonnet system prompt is the core asset. It enforces:

- Output is a single complete HTML file. No explanation, no markdown fences, no preamble.
- Required structure: `<canvas>`, `init()`, `update(dt)`, `render()`, `gameLoop()` driven by `requestAnimationFrame`.
- Required UX: title screen, game over state, restart on key press, visible score.
- Input handling via `keydown`/`keyup` state map (not event-driven movement — feels laggy).
- All assets generated procedurally (shapes, gradients). No external URLs, no CDN imports, no fetches.
- Wrap game loop in try/catch and `postMessage` errors to parent.
- Self-contained: no `<script src>`, no `<link>`, no fonts loaded externally (system font stack only).
- Single retrieved RAG example injected as a few-shot reference.
- Style tags (if extracted) injected as aesthetic guidance.

Genre-specific variants of this prompt are selected based on classification. Each variant adds genre-appropriate constraints (e.g. for `flappy`: "single-button input, gravity simulation, infinite scrolling obstacles").

For refinement, the prompt instructs Sonnet to preserve user-visible behavior unless the feedback explicitly asks for a rewrite, and grants permission to rewrite from scratch when feedback is fundamentally incompatible with current code.

**Prompt content lives outside this spec.** Full system prompt text and genre-specific variants live in `apps/server/src/services/llm/prompts/` and evolve continuously. The spec defines the *contract* (what the prompt must enforce); the file defines the *content*.

## 14. Cross-cutting Backend Concerns

### Logging (Pino)

- Fastify configured with Pino as built-in logger.
- `pino-pretty` in dev, JSON in production.
- Per-request: `requestId, userId, route, method, status, duration_ms`. `userId` is bound on a child logger by `plugins/request-context.ts` (runs after the auth guard so the session is available), so every downstream log line — including `services/llm/client.ts:logUsageOnDrain` — carries the user without explicit plumbing.
- LLM calls logged with `model, tokens_in, tokens_out, duration_ms, cost_usd`.
- `cost_usd` is computed from a per-token price table in `packages/shared/src/models.ts`, keyed by model name.
- RAG retrieval logged with `ragExampleId, similarity, genreFilter, fellBackToGlobal` — the foundational data every RAG decision needs.
- Refunds logged with `reason` (see §10 refund reasons).
- Errors logged at ERROR with full stack.
- See `docs/operations.md` for log-shipping options and field reference.

### Rate limiting

- `@fastify/rate-limit` plugin, in-memory store.
- Global per-IP: 60 req/min on all `/api/*` routes.
- Generation/refinement endpoints: additional cap of 10 req/min per user (defense-in-depth on top of credit checks).
- Rate limit responses: 429 with `Retry-After` header.
- The per-IP cap keys on `req.ip`. Behind a reverse proxy / load balancer (e.g. Fly), Fastify must be told to trust `X-Forwarded-For` or every client collapses into one bucket — set `TRUST_PROXY=true` (wired to Fastify `trustProxy` in `index.ts`; the Fly deploy sets it in `fly.toml`).

### Auth gating

- Better Auth session middleware on all `/api/*` routes except `/api/auth/*`, `/api/health`, `/api/config`, and `/api/play/*` (the public play / remix prefix; remix performs its own session check).
- The auth guard is a root-scope `preHandler` hook on the app instance — registered via a plain function call (`registerAuthGuard(app)`), not an `app.register(...)`. Fastify plugins encapsulate hooks added inside them, so attaching the guard inside a plugin would silently fail to apply to routes registered later.
- Game routes additionally check `game.user_id === session.user.id`. 404 (not 403) on mismatch to avoid leaking existence.

### CSRF defense

`plugins/csrf.ts` rejects any state-changing request (`POST` / `PATCH` / `PUT` / `DELETE`) on `/api/*` (excluding `/api/auth/*`, which Better Auth manages itself) whose `Content-Type` is not `application/json`. Returns `415 { code: "VALIDATION_ERROR" }`. This blocks the simple-cross-origin-POST attack vector that SameSite + Origin checks alone don't fully cover. Empty-body requests with no Content-Type are exempt (e.g. `POST /api/games/:id/publish` with no payload).

### Request validation

- Zod schemas on all request bodies, validated by a Fastify plugin.
- Validation errors → `400 { code: "VALIDATION_ERROR", message, details: { issues } }`.

### CORS

- Web on `http://localhost:5173` (Vite default), server on `http://localhost:3000` (Fastify).
- `@fastify/cors` configured with:
  - `origin: process.env.WEB_ORIGIN` (defaults to `http://localhost:5173`)
  - `credentials: true` (required for session cookies)
- Frontend `fetch` calls use `credentials: 'include'`.
- Better Auth configured with cross-origin cookie settings (`sameSite: 'lax'`, `secure: false` in dev).

### Concurrency

- **Maximum 1 active streaming generation per user.** Tracked in-memory in `lib/active-streams.ts` via a `Set<userId>`.
- Second concurrent request → `409 { code: "CONFLICT", message: "A generation is already in progress" }`.
- Set entry cleared in the handler's `finally` block — i.e. on stream **completion or error**, NOT on client disconnect (a disconnected stream keeps running to completion under background-stream semantics, holding the lock until it finishes). Set is also explicitly cleared on server boot (`clearActiveStreams()` in `index.ts`) so a stale flag from a crashed previous run can't lock a user out.
- Applies to `/api/games`, `/api/games/:id/refine`, and `/api/games/:id/repair`.
- The lock is in-memory and not shared across processes; a multi-instance deployment would need a Redis-backed equivalent.

### Cancellation & background streams

- The frontend uses `AbortController` to stop *reading* a stream (the "Stop" button / unmount), but this only tears down the client's fetch — it does not cancel the server's work.
- **Background-stream semantics:** when the SSE client disconnects (tab close, navigation away, network drop), the server detects it via `request.raw.on('close')`, stops writing SSE frames, but **does NOT abort the LLM call**. The model finishes, the result is persisted to `current_code`, and credits are charged as a success. The user returns to `/game/<id>` later and sees the completed game. Starting a generation is a commitment; navigating away doesn't waste the work. The route's `AbortController` exists only to satisfy the LLM-stream signal parameter and is never aborted from the route.
- The **server-side timeout** (180s, above) is therefore the only signal that can cancel an in-flight LLM call.
- Credits ARE refunded on server-side errors. The recorded reason distinguishes `abort` / `timeout` / `llm_error` / `persistence_error` (see §10).

### Server-side LLM timeout

Each streaming endpoint composes the user's `AbortSignal` with a server-side timeout via `withTimeout` in `services/llm/client.ts`:

| Action | Timeout |
|---|---|
| Generation, refinement, repair | 180s |

All three share a single 180s ceiling: large games can stream for well over a minute, and a too-tight cap truncated long outputs mid-statement (leaving the iframe with unparseable JS). See `LLM_TIMEOUT_MS` in `services/llm/client.ts`.

Composed signal aborts on whichever fires first. The `cleanup()` returned from `withTimeout` MUST be called after the stream resolves, success or failure, so the timer doesn't leak.

### SSE heartbeat

`lib/sse.ts:startHeartbeat(reply)` writes `:keep-alive\n\n` every 15 seconds. This keeps the connection warm against intermediate proxy idle timeouts during long pre-LLM fanout (classify + embed + title in parallel) and multi-second model streams. The leading `:` makes the line an SSE comment that compliant parsers ignore — the shared `useSSEStream` hook on the client skips it explicitly.

### Graceful shutdown

`SIGTERM` / `SIGINT` triggers a 30-second drain window: stop accepting new requests, wait for in-flight active-streams count to reach zero, then `app.close()`. Configured in `apps/server/src/index.ts`. Orchestrators with shorter terminationGracePeriods will kill in-flight SSE connections mid-frame.

### Health check

- `GET /api/health` — unauthenticated. Returns `{ ok: true, version: '<package version>' }`. Used for liveness checks.

## 16. Refinement Context Strategy

For refinement turns, context sent to Sonnet:

```
System prompt (refinement variant)
+ Original prompt: "..."
+ Past changes requested:
  - "make the paddle bigger"
  - "add power-ups"
+ Current code: <full HTML or summarized digest if > 2000 tokens>
+ Current request: "<user feedback>"
```

- **No past code versions sent.** The current code already encodes all past changes — re-sending old versions is redundant token spend.
- **History is a bulleted list of user prompts**, not full message objects. Cheap intent context.
- If `current_code` exceeds 2000 tokens (counted via `@anthropic-ai/tokenizer` — the prior `chars / 4` estimate ran ~30% off for HTML+JS-heavy code and was occasionally sending oversized prompts), GPT-4.1-mini summarizes into a structural digest first (function signatures, key constants, brief logic outline). Costs ~$0.001 but prevents Sonnet input from ballooning.

## 17. What Makes or Breaks This

In rough order of impact:

1. **Sonnet system prompt + RAG library** — 70% of output quality.
2. **Streaming UX** — without it, the product feels broken during 20–60s waits.
3. **Auto-repair loop** — generated games break often enough that this is essential.
4. **Genre classification accuracy** — wrong genre → wrong few-shot → worse output.
5. **Credit model honesty** — refunds on failure, free repairs. Charging users for our model's mistakes erodes trust fast.

What does *not* matter for MVP: structured GameSpec intermediate representations, version history, schemas, validators on generated code. These are v2 problems if generation proves unstable in production.

### Explicitly deferred

These were considered and pushed off:

- **Keyboard shortcuts** — needs an overlay + careful keybinding design across mobile/desktop.
- **Mobile builder** — acceptance is "tested on real iPhone Safari at < 768px"; cannot be implemented blind.
- **Code reveal disclosure** with `shiki` — adding a syntax highlighter would inflate the bundle ~1MB for a feature most users won't use.
- **Genre cards / adaptive suggestions** — depend on data we don't yet collect (`rag_examples` thumbnails, "tried genres" telemetry).
- **`routes/games.ts` split into `services/generation/run-{generation,refinement,repair}.ts`** — the testability win is achievable via Fastify `app.inject()` without the structural change. Revisit if the route file's complexity outgrows what tests can cover from the outside.
- **DB-level CHECK constraints** for the enum columns — SQLite can't `ALTER TABLE ADD CONSTRAINT`; recreating tables on a live DB isn't worth the marginal value when Zod enforces the same invariants at the route boundary.
- **Multi-example RAG, prompt summarization before embedding, `rag_quality_signals` table, style-tag retrieval** — all benefit from baseline retrieval logs (just shipped) before being meaningfully evaluated.
- **Lefthook pre-commit hook** — pre-commit gate is documented in AGENTS.md and works without an extra dep.
- **Seed script** — needs a curated game corpus to be useful.
- **PostHog analytics, conversion funnel, in-app feedback widget, admin dashboard, set-credits dev tool, CHANGELOG, CONTRIBUTING** — not deploy-blocking; revisit post-launch with usage data in hand.

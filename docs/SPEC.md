# ArcadeAI — Specification

## 1. Overview

ArcadeAI is a CodeWisp-style web app that turns natural-language prompts into playable 2D browser games. Users sign in, type a prompt, and watch a single-file HTML5 canvas game stream into an iframe within seconds. They iterate on the result via a chat loop, manage their library of games from a dashboard, and operate within a credit-based usage model with tiered plans.

The core architectural bet: **single-file HTML5 canvas games, generated by a strong LLM, executed in a sandboxed iframe, refined through a chat loop, scoped to authenticated users with persistent storage.**

This is a local prototype. No production deployment, no real billing, no external email. The architecture is structured so a future productionization path is straightforward (swap SQLite for Postgres, wire Stripe into the existing billing endpoint, add a real email provider).

## 2. Scope

### In scope

- OAuth authentication via Google and GitHub (no email/password)
- Default display name from OAuth profile, falls back to `user-{8 hex chars}` if blank, user-editable
- Multi-game dashboard per user (grid of game cards with screenshot thumbnails)
- Single-file HTML + JS games using HTML5 Canvas
- 2D arcade genres: paddle, snake, flappy, shooter, platformer, puzzle, runner, other
- Prompt → game in one shot (streaming)
- Refinement via follow-up instructions
- Auto-repair on runtime errors (capped attempts)
- Credit-based usage model with daily and monthly caps
- Tiered plans: Free, Creator, Pro, Enterprise (display only) + internal Admin tier
- Pricing page with monthly/yearly toggle (upgrade buttons are no-ops in prototype)
- User dropdown with usage bars, plan badge in top bar
- Profile settings page
- Dark/light mode toggle
- Pino-based structured logging on all backend requests
- Per-IP rate limiting
- RAG library of curated reference games for few-shot prompting

### Out of scope (MVP)

- Real billing (Stripe integration is structured-for but not implemented)
- Email verification, password reset emails, any outbound email
- Sharing games publicly, version history UI, code editor in the browser
- Multi-file game projects, frameworks, backends inside generated games
- 3D, multiplayer, mobile-native
- Asset generation (sprites, audio files)
- Production deployment, multi-instance scaling
- Mobile responsiveness for the builder view (dashboard and pricing are responsive; builder is desktop-only)
- Tests (added incrementally as components stabilize)

### Models

| Model | Role |
|---|---|
| Claude Sonnet 4.6 (`claude-sonnet-4-6`) | **Runtime:** game generation, refinement, auto-repair (anything where output quality determines whether the game is fun) |
| Claude Opus 4.7 (`claude-opus-4-7`) | **Build-time only:** drafting the RAG reference library (~20 hand-curated games). Not used at runtime. See §8. |
| GPT-4.1-mini (`gpt-4.1-mini`) | Genre classification, style tag extraction, code summarization, error categorization, game title generation |
| text-embedding-3-small | Prompt embeddings for RAG retrieval |

Model IDs are pinned in `packages/shared/src/models.ts` so they're swappable in one place.

The split keeps cost low on bulk operations while reserving Sonnet for the work that actually determines quality.

## 5. Data Model

### Tables

```ts
// users — extended from Better Auth's user table
users
  id              text primary key (better-auth uuid)
  email           text unique not null     // sourced from OAuth provider
  display_name    text not null            // OAuth name field, or 'user-{8 hex}' if blank. Not unique.
  tier            text not null            // 'free' | 'creator' | 'pro' | 'admin'
  credits_remaining_daily   integer not null
  credits_remaining_monthly integer not null
  daily_reset_at    integer not null  // unix ms, next UTC midnight
  monthly_reset_at  integer not null  // unix ms, first of next month UTC
  theme           text not null default 'dark'  // 'dark' | 'light' | 'system'
  created_at      integer not null
  updated_at      integer not null

games
  id              text primary key (uuid)
  user_id         text not null references users(id) on delete cascade
  title           text not null
  current_code    text not null     // the latest single-file HTML
  thumbnail       text              // base64 PNG data URL or null
  genre           text              // classified genre bucket
  original_prompt text not null
  created_at      integer not null
  updated_at      integer not null

messages
  id              text primary key (uuid)
  game_id         text not null references games(id) on delete cascade
  kind            text not null     // 'prompt' | 'feedback'
  content         text not null     // the user's prompt or refinement feedback (verbatim)
  created_at      integer not null

// Note: assistant output (generated HTML) is NOT stored here. Only the *latest* HTML
// lives in `games.current_code`. Auto-repair attempts are NOT stored as messages
// (they're already tracked in `usage_log` with action='repair'). The chat panel
// renders user messages with implicit "→ Generated game" markers between entries.

usage_log
  id              text primary key (uuid)
  user_id         text not null references users(id) on delete cascade
  game_id         text references games(id) on delete set null
  action          text not null     // 'generation' | 'refinement' | 'repair' (repair logged but charges 0)
  credits_charged integer not null
  succeeded       integer not null  // 0 or 1
  created_at      integer not null

// RAG library — curated reference games
rag_examples
  id              text primary key
  genre           text not null     // one of the 8 genre buckets
  prompt          text not null     // the prompt that would describe this example
  html            text not null     // the full single-file HTML
  created_at      integer not null

// vec0 virtual table for embeddings, joined to rag_examples by id
rag_embeddings    vec0 virtual table (id text primary key, embedding float[1536])
```

The `vec0` virtual table cannot be expressed in Drizzle's schema DSL. It's created via a **post-migration raw SQL step** that runs after Drizzle migrations: `CREATE VIRTUAL TABLE IF NOT EXISTS rag_embeddings USING vec0(id text primary key, embedding float[1536])`. This is a one-line script in `packages/db/src/post-migrate.ts` invoked after `drizzle-kit migrate`.

Better Auth's `session` and `account` tables live alongside, managed by the library. The `account` table stores per-provider OAuth tokens and linkage (one row per linked provider per user).

The `users` table extends Better Auth's built-in `user` table with our custom columns (`tier`, `credits_remaining_*`, `*_reset_at`, `theme`, `display_name`) using Better Auth's schema customization (additional fields are declared in the auth config and Better Auth includes them in its generated migrations). On first sign-in, Better Auth's `databaseHooks.user.create.before` callback populates our extended fields (admin tier check, initial credit allotment, default display_name).

### Key design points

- **Latest-only code storage.** No version history in MVP. Each refinement overwrites `games.current_code`.
- **Optimistic credit deduction with refund on failure.** Credits decremented at request start, refunded only if the action fails unrecoverably (not on auto-repaired errors — those are our problem, not the user's).
- **Daily and monthly counters reset lazily on read** (compare current time to `*_reset_at` and reset if past).
- **All timestamps are unix milliseconds (integer)** for SQLite compatibility and JS interop.

## 6. Genre & Style Classification

### Genre buckets (8)

`paddle, snake, flappy, shooter, platformer, puzzle, runner, other`

Drives RAG retrieval. `other` falls back to no genre filter (nearest-neighbor across the whole library).

### Style tags

Free-form aesthetic descriptors extracted by GPT-4.1-mini (e.g. `retro`, `neon`, `minimal`, `cute`, `dark`). Injected into the Sonnet system prompt as guidance, not used for retrieval.

### Classification call

Single GPT-4.1-mini call (structured output / JSON mode) returns:
```json
{ "genre": "shooter", "style_tags": ["retro", "neon"] }
```

Done in parallel with the embedding call to minimize latency.

### Failure handling

If the classification call returns malformed JSON, an invalid genre, or fails entirely:
- Default to `genre: "other"`, `style_tags: []`
- Log the failure at WARN level with the raw response
- Continue the pipeline (RAG falls back to global nearest-neighbor on `other`)

Generation should never block on classification failure.

## 7. Generation Pipeline

### Initial generation

```
POST /api/games  (game row created immediately with placeholder title;
                  prompt persisted as messages row with kind='prompt')
    ↓
SSE 'meta' event sent: { gameId, placeholderTitle }  (client replaceState → /game/:id)
    ↓
[parallel]
  ├─ GPT-4.1-mini: classify genre + extract style tags
  ├─ text-embedding-3-small: embed prompt
  └─ GPT-4.1-mini: generate game title (PATCH /api/games/:id when complete)
    ↓
sqlite-vec: retrieve top 1 example, filtered by genre
    ↓
Claude Sonnet 4.6: generate single-file HTML (streamed)
    ↓
Stream HTML tokens to client via SSE 'chunk' events
    ↓
Client renders into iframe via srcdoc
    ↓
Client captures thumbnail after ~2s, POSTs to /api/games/:id/thumbnail
```

The placeholder title is the first 40 chars of the prompt. The generated title arrives via the next dashboard load or by polling/refetching `/api/games/:id`. The original prompt is also stored on `games.original_prompt` for use in refinement context.

### Refinement

```
User feedback (persisted as messages row with kind='feedback') + current code
    ↓
If currentCode > 2000 tokens (estimated as chars/4): GPT-4.1-mini summarizes into structural digest
    ↓
Build context: original prompt + bulleted history of past user requests + current code (or digest)
    ↓
Claude Sonnet 4.6: generate updated HTML (system prompt allows full rewrite if feedback is incompatible with current code)
    ↓
Stream HTML, replace iframe srcdoc, recapture thumbnail
```

### Auto-repair

```
iframe postMessage('game-error', {message, stack})
    ↓
Show "Detected an error, fixing..." indicator
    ↓
GPT-4.1-mini: categorize error (syntax / runtime / logic)
    ↓
Claude Sonnet 4.6: repair (current code + error + original prompt)
    ↓
Stream replacement HTML
    ↓
If a 2nd repair fails: show error to user with "Try again" (re-runs original prompt) and "Refine" (treats as refinement turn) buttons
```

Auto-repair is **free** — credits are not charged. The model failed, not the user. Each repair attempt still gets a `usage_log` row with `action='repair'`, `credits_charged=0`, and `succeeded` set on completion (for observability — we want to know how often repairs happen and how often they work).

## 8. RAG Library

### Sourcing

**Generate-then-curate, build-time only.** Target ~20 games at launch (~2–3 per genre bucket).

The reference library is the highest-leverage code in the entire system — every runtime generation retrieves one of these examples and shows it to Sonnet as a "build something like this" reference. A 5% better reference compounds across thousands of generations.

**Model requirement: Claude Opus 4.7 (NOT Sonnet) for drafting reference games.**

- Opus produces meaningfully better long-form code coherence, subtle correctness, and structural faithfulness than Sonnet — exactly the qualities that matter for a reference asset.
- Cost is trivial: ~$0.25 per game × 20 games = **~$5 one-time**, since this runs once at build time, not in user-facing runtime.
- Each draft is then hand-edited until it cleanly satisfies the system prompt's structural rules (canvas, gameLoop, title screen, etc.) and plays well.
- Runtime model selection is unaffected: Sonnet remains the runtime model for all user-facing generation, refinement, and repair.

### Implementation note (separate doc)

The reference library has its own scope — a build-time script, an editorial process, embedding generation, and seeding the database. **It will be planned and executed in its own design doc** (`docs/designs/rag-library.md` or similar) separately from the main app. The main app's build order assumes the seeded library exists by step 8.

### Retrieval

- **Exactly 1 example** per generation request. Two examples confuse the model and double input tokens; one strong example is more effective.
- **Full code injected** into the system prompt as a few-shot reference. Skeletons lose the concrete pattern that makes few-shot work.
- **Filtered by classified genre**, then nearest-neighbor by embedding cosine similarity within that filter. `other` genre falls back to global nearest-neighbor.

### Storage

- `rag_examples` holds the metadata + HTML.
- `rag_embeddings` is a `vec0` virtual table holding the 1536-dim embeddings.
- Single SQL query: `SELECT html FROM rag_examples WHERE id IN (SELECT id FROM rag_embeddings WHERE genre = ? ORDER BY vec_distance_cosine(embedding, ?) LIMIT 1)`.

## 9. Sandboxing & Error Handling

### iframe setup

- `<iframe srcdoc={generatedHTML} sandbox="allow-scripts">` (no `allow-same-origin` — that would let generated code escape).
- A wrapper script is injected into the bottom of every generated HTML before assignment to `srcdoc`:

```js
window.addEventListener('error', (e) => {
  parent.postMessage({type: 'game-error', message: e.message, stack: e.error?.stack}, '*');
});
window.addEventListener('unhandledrejection', (e) => {
  parent.postMessage({type: 'game-error', message: String(e.reason)}, '*');
});
```

### Error scope

- **Hard crashes only** trigger auto-repair (uncaught exceptions, unhandled promise rejections).
- Silent failures (black canvas, no rAF) are not auto-detected — too many false positives kill UX more than the bug does.
- Logic bugs (ball goes through paddle) are user-detected and handled via refinement turns.

### Repair lifecycle

1. Error caught → show "Detected an error, fixing..." indicator (visible, not silent).
2. Categorize → repair → stream replacement.
3. Cap at 2 attempts.
4. After 2 failures: surface error to user with truncated message, collapsible code panel, and two CTAs (Try again / Refine).

### iframe lifecycle on refinement

Hard reload — replacing `srcdoc` re-runs the game from scratch. No hot-swap.

## 10. Plan Tiers & Credit Model

### Internal credit costs

| Action | Cost |
|---|---|
| Generation | 200 credits |
| Refinement | 150 credits |
| Auto-repair | 0 (free — our bug, not yours) |

### Tiers

| Tier | Price (mo) | Price (yr) | Credits | Notes |
|---|---|---|---|---|
| Free | $0 | $0 | 3,000/month, 500/day cap | Public default |
| Creator | $15 | $13/mo ($156 billed yearly, -15%) | 20,000/month | Public |
| Pro | $29 | $25/mo ($300 billed yearly, -15%) | 50,000/month | Public |
| Enterprise | Custom | Custom | Custom | Display only — "Contact Sales" no-op |
| Admin | — | — | Unlimited | Internal only, not shown on pricing page. Bypasses all credit checks. |

### Admin assignment

- `ADMIN_EMAILS` env var (comma-separated).
- On first sign-in, if `email` matches an entry, `tier` is set to `'admin'` automatically (via Better Auth's `databaseHooks.user.create.before`).
- Admin users see "Admin (unlimited)" in the usage dropdown instead of fractional bars.

### Credit lifecycle

1. Request arrives → check `credits_remaining_*` >= action cost.
2. If insufficient → 402 Payment Required with reset time.
3. If sufficient → deduct optimistically, log to `usage_log` with `succeeded = 0`.
4. On unrecoverable failure → refund credits, leave log row marked `succeeded = 0`.
5. On success (including auto-repaired) → mark log row `succeeded = 1`.

### Reset behavior

- **Daily counter:** resets at UTC midnight. Lazy reset on read.
- **Monthly counter:** resets at first of month UTC. Lazy reset on read.
- **Plan downgrade:** immediate reset to new tier's allotment.
- **Plan upgrade:** immediate top-up to new tier's allotment.

## 11. Backend API

All routes prefixed with `/api`. Auth required except where noted.

### Auth (Better Auth handles these)

- `GET  /api/auth/sign-in/google` — initiate Google OAuth flow
- `GET  /api/auth/sign-in/github` — initiate GitHub OAuth flow
- `GET  /api/auth/callback/google` — OAuth callback (creates user on first sign-in)
- `GET  /api/auth/callback/github` — OAuth callback (creates user on first sign-in)
- `POST /api/auth/sign-out`
- `GET  /api/auth/session` — current session/user
- `POST /api/auth/link/google` — link Google account to existing session
- `POST /api/auth/link/github` — link GitHub account to existing session

On first sign-in:
- User row created with email from OAuth provider
- `display_name` set to provider's name field, or `user-{8 hex}` if blank
- `tier` set to `admin` if email matches `ADMIN_EMAILS`, otherwise `free`
- Initial credit allotment granted

### Generation

- `POST /api/games` — create new game, runs full generation pipeline. Streams SSE. Body: `{ prompt: string }`. Charges 200 credits. Returns `{ gameId, placeholderTitle }` in initial `meta` event (final title arrives later via PATCH), then streams HTML chunks.
- `POST /api/games/:id/refine` — refinement turn. Streams SSE. Body: `{ feedback: string }`. Charges 150 credits.
- `POST /api/games/:id/repair` — auto-invoked by the client when the iframe reports an error via postMessage. Streams SSE. Body: `{ error: { message, stack } }`. Free (charges 0 credits but logged in `usage_log`).

### Game CRUD

- `GET    /api/games` — list current user's games (id, title, thumbnail, updated_at). For dashboard.
- `GET    /api/games/:id` — full game (code + messages history). For loading a game in builder.
- `PATCH  /api/games/:id` — update title (only mutable field exposed).
- `POST   /api/games/:id/thumbnail` — body: `{ thumbnail: string }` (base64 data URL).
- `DELETE /api/games/:id` — hard delete.

### User & usage

- `GET   /api/me` — current user with usage stats (daily + monthly remaining, reset times, tier, linked providers).
- `PATCH /api/me` — update display_name or theme.
- `DELETE /api/me` — delete account + all games + all linked OAuth accounts.

### Billing (no-op in prototype)

- `POST /api/billing/change-plan` — body: `{ tier: 'free' | 'creator' | 'pro', interval: 'monthly' | 'yearly' }`. In prototype, immediately updates user's tier and resets credits. Structured so a future Stripe webhook can replace the immediate update.

### Health

- `GET /api/health` — unauthenticated. Returns `{ ok: true, version: '<package version>' }`. Used for liveness checks and as the smoke test in build step 1.

### SSE streaming format

All streamed endpoints emit `text/event-stream` with these event types:
- `meta` — initial metadata (`{ gameId, placeholderTitle }`). Sent immediately after game row creation, before any LLM work. Final title arrives later when title generation completes (next `GET /api/games/:id` reflects it).
- `chunk` — HTML token (`{ delta: string }`)
- `error` — terminal failure (`{ message: string, code?: string }`)
- `done` — terminator only (`{}`). Client already has full code from accumulated chunks.

Split-pane, ~35/65 left/right.

**Right (game iframe):**
- `<iframe srcdoc={code} sandbox="allow-scripts">` filling the pane

- Control bar below iframe: **Regenerate** (re-runs original prompt as a fresh generation, charges credits)
- The iframe wrapper script (error postMessage handlers from §9) is **injected client-side** before assignment to `srcdoc`. Server stores only the LLM's raw output as `current_code`; the wrapper is never persisted.

### Auth flows

**Sign-in:**
1. Unauthenticated user lands on `/` → redirected to `/sign-in` (preserves `next` param)
2. `/sign-in` shows two buttons: "Continue with Google", "Continue with GitHub"
3. Click → OAuth round-trip → callback creates user (first sign-in) or restores session
4. Redirect to `next` param or `/` (dashboard) by default. New users see the empty-state dashboard CTA.

**Sign-out:**
1. User dropdown → "Sign out" → `POST /api/auth/sign-out`
2. On success, hard navigation to `/sign-in` (clears all client state including TanStack Query cache)

### Game creation flow

1. Dashboard → click "+ New Game" → routes to `/game/new`
2. Empty builder, prompt input focused
3. User types prompt, submits
4. Server creates the game record at the start of `POST /api/games` (before any LLM work) and returns the new `gameId` + placeholder title in the SSE `meta` event
5. Client receives `meta`, calls `history.replaceState` to swap `/game/new` → `/game/:id` with no remount
6. Streaming continues into the same component instance

## 13. System Prompt Strategy (Sonnet)

We maintain three Sonnet prompt families — all running on Claude Sonnet 4.6:
- **Generation prompt** (with per-genre variants) — initial single-shot game creation
- **Refinement prompt** — applies user feedback to existing code
- **Repair prompt** — fixes a runtime error in existing code

The shared base contract below applies to all three. Variants extend it with task-specific instructions.

### Base contract

The Sonnet system prompt is the core asset. It enforces:

- Output is a single complete HTML file. No explanation, no markdown fences, no preamble.
- Required structure: `<canvas>`, `init()`, `update(dt)`, `render()`, `gameLoop()` driven by `requestAnimationFrame`.
- Required UX: title screen, game over state, restart on key press, visible score.
- Input handling via `keydown`/`keyup` state map (not event-driven movement — feels laggy).
- All assets generated procedurally (shapes, gradients). No external URLs, no CDN imports, no fetches.
- Wrap game loop in try/catch and `postMessage` errors to parent.
- Self-contained: no `<script src>`, no `<link>`, no fonts loaded externally (system font stack only).
- Single retrieved RAG example injected as a few-shot reference.
- Style tags (if extracted) injected as aesthetic guidance.

Genre-specific variants of this prompt are selected based on classification. Each variant adds genre-appropriate constraints (e.g. for `flappy`: "single-button input, gravity simulation, infinite scrolling obstacles").

For refinement, the prompt instructs Sonnet to preserve user-visible behavior unless the feedback explicitly asks for a rewrite, and grants permission to rewrite from scratch when feedback is fundamentally incompatible with current code.

**Prompt content lives outside this spec.** Full system prompt text and genre-specific variants live in `apps/server/src/services/llm/prompts/` and evolve continuously. The spec defines the *contract* (what the prompt must enforce); the file defines the *content*.

## 14. Cross-cutting Backend Concerns

### Logging (Pino)

- Fastify configured with Pino as built-in logger.
- `pino-pretty` in dev, JSON in production.
- Per-request: `requestId, userId, route, method, status, duration_ms`.
- LLM calls logged separately with the same `requestId` for correlation: `requestId, model, tokens_in, tokens_out, duration_ms, cost_usd`.
- `cost_usd` is computed from a per-token price table in `packages/shared/src/models.ts` (alongside the model IDs), keyed by model name.
- Errors logged at ERROR with full stack.

### Rate limiting

- `@fastify/rate-limit` plugin, in-memory store.
- Global per-IP: 60 req/min on all `/api/*` routes.
- Generation/refinement endpoints: additional cap of 10 req/min per user (defense-in-depth on top of credit checks).
- Rate limit responses: 429 with `Retry-After` header.

### Auth gating

- Better Auth session middleware on all `/api/*` routes except `/api/auth/*` and `/api/health`.
- Game routes additionally check `game.user_id === session.user.id`. 404 (not 403) on mismatch to avoid leaking existence.

### Request validation

- Zod schemas on all request bodies, validated by a Fastify plugin.
- Validation errors → 400 with field-level error messages.

### CORS

- Web on `http://localhost:5173` (Vite default), server on `http://localhost:3000` (Fastify).
- `@fastify/cors` configured with:
  - `origin: process.env.WEB_ORIGIN` (defaults to `http://localhost:5173`)
  - `credentials: true` (required for session cookies)
- Frontend `fetch` calls use `credentials: 'include'`.
- Better Auth configured with cross-origin cookie settings (`sameSite: 'lax'`, `secure: false` in dev).

### Concurrency

- **Maximum 1 active streaming generation per user.** Tracked in-memory via a `Set<userId>`.
- Second concurrent request → 409 Conflict with `{ error: 'A generation is already in progress' }`.
- Set entry cleared on stream completion, error, or client disconnect.
- Applies to `/api/games`, `/api/games/:id/refine`, and `/api/games/:id/repair`.

### Cancellation

- Frontend uses `AbortController` on streaming requests.
- Server detects client disconnect via `request.raw.on('close')` and aborts the LLM stream via the AI SDK's abort signal.
- **Credits are NOT refunded on user-initiated cancel** — tokens have already been spent up to the abort point.
- Credits ARE refunded on server-side errors (LLM API failure, timeout, validation errors after deduction).

### Health check

- `GET /api/health` — unauthenticated. Returns `{ ok: true, version: '<package version>' }`. Used for liveness checks.

## 16. Refinement Context Strategy

For refinement turns, context sent to Sonnet:

```
System prompt (refinement variant)
+ Original prompt: "..."
+ Past changes requested:
  - "make the paddle bigger"
  - "add power-ups"
+ Current code: <full HTML or summarized digest if > 2000 tokens>
+ Current request: "<user feedback>"
```

- **No past code versions sent.** The current code already encodes all past changes — re-sending old versions is redundant token spend.
- **History is a bulleted list of user prompts**, not full message objects. Cheap intent context.
- If `current_code` exceeds 2000 tokens (estimated as `chars / 4` — no tokenizer needed), GPT-4.1-mini summarizes into a structural digest first (function signatures, key constants, brief logic outline). Costs ~$0.001 but prevents Sonnet input from ballooning.

## 17. What Makes or Breaks This

In rough order of impact:

1. **Sonnet system prompt + RAG library** — 70% of output quality.
2. **Streaming UX** — without it, the product feels broken during 20–60s waits.
3. **Auto-repair loop** — generated games break often enough that this is essential.
4. **Genre classification accuracy** — wrong genre → wrong few-shot → worse output.
5. **Credit model honesty** — refunds on failure, free repairs. Charging users for our model's mistakes erodes trust fast.

What does *not* matter for MVP: structured GameSpec intermediate representations, version history, schemas, validators on generated code. These are v2 problems if generation proves unstable in production.

## 18. Cost Model (rough)

Per generation:
- GPT-4.1-mini classify + title + embedding: ~$0.0005
- Claude Sonnet 4.6 generation (avg 3K input incl. RAG example, 4K output): ~$0.07
- **Total: ~$0.07 per generation**

Per refinement:
- GPT-4.1-mini summarize (if triggered): ~$0.003
- Claude Sonnet 4.6 refinement: ~$0.05
- **Total: ~$0.05 per refinement**

Per auto-repair:
- GPT-4.1-mini categorize: ~$0.0001
- Claude Sonnet 4.6 repair: ~$0.05
- **Total: ~$0.05 per repair (free to user)**

Worst-case per-user cost by tier:
- Free (3,000 cr/mo = ~15 gen + 0 ref OR 0 gen + 20 ref): ~$1/mo
- Creator (20,000 cr/mo): ~$7/mo (53% margin at $15/mo)
- Pro (50,000 cr/mo): ~$17/mo (41% margin at $29/mo)
